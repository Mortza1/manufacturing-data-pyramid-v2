This is a targeted Stage 4 Connections refactor. The key principle is:

Loops are the primary user-facing entities. Individual directional connections are ordered segments within a loop.

Preserve Structure, Data, Visualise, Explorer and Forging Case Study. Do not implement Stage 5 Save/database, Advanced mode, Models, Agents or Decisions.

1. First fix the current arrow endpoint bug

The read-only inspection identified the exact cause:

visible data objects are children of a level group rotated around Y;
for four sectors the level group uses a 45° Y rotation;
current arrow endpoints use grid-derived X/Z coordinates but do not apply that same level rotation;
therefore arrows visibly start/end in empty space.

Fix this before the loop UX refactor.

Create one shared helper for the actual rendered/world position of a v2 data object and use it consistently for arrow endpoints.

It must include:

level vertical centre;
Explode offset;
object local vertical offset;
sector/level Y rotation;
grid-derived X/Z location;
relevant presentation transforms.

Do not calculate connection endpoints from incomplete local coordinates.

Arrows must visibly begin at the source object and terminate at the target object.

Use a conservative shape-aware or mesh-boundary attachment offset so arrowheads do not sit obviously inside the target object or float far away from it.

Preserve all canonical object fields:

level_id
sector_id
grid_x
grid_y

2. Introduce a first-class Loop entity

The current implementation only stores a loop name string independently on every connection.

Replace this with a real loop model.

Each loop should have:

stable loop ID;
name;
description;
colour;
optional closed/open status;
ordered connection segments.

Each connection segment should contain:

stable connection ID;
loop_id;
sequence/order;
source_object_id;
target_object_id;
direction;
optional segment label;
optional segment description/note.

Loop colour belongs primarily to the loop so all segments use the same colour.

3. Safely migrate existing connections

Do not silently discard the connections already created in this v2 case.

Migrate existing data by:

grouping current connections by normalized loop/group string;
creating one loop entity for each group;
preserving existing connection IDs;
preserving source/target, labels and descriptions;
assigning each migrated segment a deterministic sequence;
using a sensible loop colour derived from the existing connection colours;
putting blank/unassigned relationships into an Unassigned loop if required.

Do not modify data objects.

Replace the main Create New Connection workflow with:

Create New Loop

Optional description
Loop colour

Then begin a continuous node-selection workflow:

Select first data element

Select next data element

A → B

Select the next data element

B → C

and so on.

Continue until the user chooses:

Do not allow self-connections, immediately repeated nodes or duplicate segments within the same loop.

start → current path → current endpoint → next selection
